# API reference

FastAPI app `pinance_ml_inference.api:app` (title "Pinance ML Inference (local)"). Interactive docs are generated by FastAPI at `/docs`.

The request and response bodies below are written from [`api.py`](../src/pinance_ml_inference/api.py), [`predict.py`](../src/pinance_ml_inference/predict.py) and [`model_registry.py`](../src/pinance_ml_inference/model_registry.py). The shapes were checked against a real running process with toy models and a directory instead of MinIO ([offline demo](offline-demo.md), captured in [`examples/toy_demo_outputs/`](examples/toy_demo_outputs/)); they were **not** captured from a production deployment. The status codes and the request rules are exercised by `tests/test_api_predict.py` (in-process, stubbed models). Values written as `…` or as a type name are placeholders; the shapes are the ones the code returns and the unit tests assert on.

## `GET /health`

```json
{ "status": "ok" }
```

Liveness only; it does not look at models or MinIO.

## `GET /models`

What is loaded, per symbol and slot, and the feature-schema fingerprint this service expects per symbol. Training's auto-promotion reads `expected_schema_version`. The symbol list comes from the database; if the database is down the endpoint still answers with the symbols already held in memory (`test_get_models_still_answers_when_db_is_down`).

```jsonc
{
  "expected_schema_version": { "BTCUSDT": "38b98fc7516d", "ETHUSDT": "f72fb5b8ba97" },
  "models": {
    "BTCUSDT": {
      "production": {
        "loaded": true,
        "last_load_error": null,
        "model_version": "<string>",
        "schema_version": "<12 hex>",
        "matches_expected": true,
        "quantile": {
          "status": "loaded",               // loaded | absent | ignored_schema_mismatch
          "quantile_model_version": "<string or null>",
          "quantile_schema_version": "<12 hex or null>"
        }
      },
      "candidate": { "loaded": false, "last_load_error": null }
    }
  }
}
```

The two fingerprints shown (`38b98fc7516d` for BTCUSDT with 93 features, `f72fb5b8ba97` for the other symbols with 94) are real: they are what the vendored feature code produces and what [`tests/fixtures/training_schema_vectors.json`](../tests/fixtures/training_schema_vectors.json) pins.

Reading it:

| Observation | Meaning |
|---|---|
| `loaded: false`, `last_load_error: null` | the slot is empty (normal for `candidate`) or has not been polled yet |
| `loaded: false`, `last_load_error: "…"` | a push was rejected and nothing older was loaded; the text says why (feature list, `schema_version` label, or booster names) |
| `loaded: true`, `last_load_error: "…"` | either a **newer** push was rejected and the older set keeps serving, or the corridor was ignored (`quantile.status` is then `ignored_schema_mismatch`) |
| `matches_expected: false` | the loaded set's fingerprint differs from the expected one |

A rejected state is covered by `test_models_status_reports_loaded_rejected_and_expected`; the error clearing once a good version loads by `test_rejection_error_clears_once_a_good_version_loads`.

## `POST /predict/{symbol}` and `POST /predict/{symbol}/shadow`

The first answers from the `production` slot, the second from `candidate`. Same request, same response. `{symbol}` is upper-cased (`btcusdt` works).

### Request

```jsonc
{
  "as_of_ts": "2026-10-01T12:00:00Z",
  "candles": {
    "ETHUSDT": [ { "ts": "…", "open": 0.0, "high": 0.0, "low": 0.0, "close": 0.0, "volume": 0.0 }, … ],
    "BTCUSDT": [ … ]
  }
}
```

| Rule | Detail |
|---|---|
| `candles[SYMBOL]` | at least 150 candles; the last candle's `ts` must equal `as_of_ts`; unsorted input is sorted |
| `candles["BTCUSDT"]` | required, with at least 150 candles, whenever the symbol is not BTCUSDT (cross-asset feature `btc_ret`); ignored for BTCUSDT |
| `ts` | ISO 8601; a value without an offset is treated as UTC |
| Closed candles | the service cannot tell closed from open candles; the caller is responsible |

### Response

```jsonc
{
  "symbol": "BTCUSDT",
  "as_of_ts": "<ISO 8601>",
  "close": 0.0,                         // close of the as_of_ts candle
  "model_version": "<string or null>",
  "quantile_model_version": "<string or null>",
  "schema_version": "<12 hex or null>",
  "inference_ms": 0.0,                  // time spent in the 12 horizons' booster calls only
  "feature_count": 93,                  // 94 for non-BTC symbols
  "feature_baseline": { … },            // from metadata.json, or null
  "feature_snapshot": {                 // raw values for the predicted row; null where undefined
    "btc_ret": null, "atr": 0.0, "bb_width": 0.0, "rsi": 0.0, "ret_std_144": 0.0, "macd_diff": 0.0
  },
  "predictions": [
    {
      "horizon": 1,
      "target_ts": "<as_of_ts + 5 min * horizon>",
      "r_pred": 0.0, "price_pred": 0.0,
      "r_q10": 0.0, "r_q90": 0.0, "price_q10": 0.0, "price_q90": 0.0   // only when a corridor is loaded
    }
    // … horizons 2 to 12
  ]
}
```

- `r_*` are log-returns `log(P[t+5h min] / P[t])`; `price_* = close * exp(r_*)`.
- `feature_snapshot.btc_ret` is `null` for BTCUSDT itself (the feature does not exist there).
- `inference_ms` does not include feature computation, request parsing or the network.
- Without a corridor (point-only or ignored) the `*_q10` / `*_q90` fields are absent, not null.
- With a corridor the order `r_q10 ≤ r_pred ≤ r_q90` always holds ([decision 8](design-decisions.md#8-quantile-crossing-is-repaired-not-hidden)).

### Errors

| Status | When | Source |
|---|---|---|
| 404 | no model is loaded for that symbol and slot (never polled, empty slot, or rejected on first load). For `/shadow` this is the normal "nothing to test" answer | `ModelNotLoadedError` |
| 422 | fewer than 150 candles for the symbol, or for BTCUSDT when required | `InsufficientHistoryError` |
| 422 | `as_of_ts` differs from the last candle's `ts` | `AsOfMismatchError` |
| 422 | malformed body (missing field, wrong type) | FastAPI / pydantic validation |

The model check comes first: a symbol with nothing loaded answers 404 even if the window is also bad. The exceptions raised by `predict()` are covered by `tests/test_predict.py`; the mapping to status codes (`_predict_or_404`) by `tests/test_api_predict.py`, which sends requests through FastAPI's `TestClient` with a stubbed model registry.
